# Шаблон проекта: мультиагентная ИИС с RAG

Заготовка индивидуального проекта: мультиагентная интеллектуальная информационная
система с RAG, сессионной памятью, слоем безопасности и двумя каналами доставки.
Собирается за восемь практик, 5 семестр.

> **Студенту.** Это стартовая точка работы, а не готовая система: учебные
> модули содержат заглушки, которые будут заполняться в процессе разработки учебного проекта.

### User Stories

- Как владелец магазина, я хочу проверить максимально допустимый размер вывески, чтобы не получить штраф при установке.
- Как дизайнер, я хочу получить список цветовых ограничений, чтобы согласовать эскиз с архитектурным управлением.
- Как юрист, я хочу найти все пункты 38-ФЗ, где упоминаются «световые короба», чтобы подготовить возражение на предписание.

### Архитектурные рамки

**Входит в MVP:**
- Загрузка 3 нормативных документов (38-ФЗ, ГОСТ, 902-ПП) в векторную БД.
- Обработка вопросов на русском языке через RAG + LLM.
- Возврат ответа с цитатой из документа и номером статьи/пункта.
- Сессионная память на 5 последних вопросов.
- Веб-чат и VK-бот единственные каналы доставки.
- Фильтрация входных запросов от XSS и SQL-инъекций.

**Не входит в MVP:**
- Документы других регионов РФ
- Распознавание изображений (OCR, компьютерное зрение)
- Автоматическое обновление документов
- Ответы на вопросы, выходящие за пределы загруженных документов
- Кеширование частых запросов
- Масштабирование на высокие нагрузки
- Голосовой ввод / вывод

## Часть 2. Как запустить

### Заведите репозиторий

Шаблон выдаётся архивом через систему дистанционного обучения. Распакуйте его и заведите репозиторий сами: история коммитов входит в приёмку.

```bash
cd my-project
git init -b main
git add -A && git commit -m "Стартовый шаблон"
```

**Проверьте, что распаковались файлы, начинающиеся с точки:** `.gitignore` и `.env.example`. Многие распаковщики и файловые менеджеры скрывают их по умолчанию, а без `.gitignore` в репозиторий уедут база данных, скачанная модель и, в худшем случае, ваш `.env` с ключами.

```bash
ls -a          # должны быть видны .gitignore и .env.example
```

### Как сдаётся работа

Одним файлом через систему дистанционного обучения:

```bash
git bundle create Фамилия-П1.bundle --all
```

Бандл — это весь репозиторий в одном файле: полная история, все ветки. В него попадает ровно то, что отслеживает git, поэтому `.venv`, `data/chroma/` и скачанные модели внутрь не уедут. Если вы работаете на своём устройстве и завели репозиторий на хостинге, вместо бандла можно сдать ссылку на него.

### Установка

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env        # затем заполните ключи в .env
```

### Наполнение базы знаний

Положите документы (PDF, TXT, MD) в `data/raw/`, затем:

```bash
python ingest.py          # пересобрать индекс и сразу замерить hit-rate@5
python ingest.py --eval   # только замер, без переиндексации
```

`ingest.py` собирает индекс заново: коллекция очищается перед наполнением.
Поэтому при подборе `CHUNK_SIZE` и `CHUNK_OVERLAP` на П2 достаточно поправить
`config.py` и запустить скрипт снова — удалять `data/chroma/` руками не нужно.

### Запуск

```bash
streamlit run app.py     # веб-интерфейс
python vk_bot.py         # бот в VK
python test_suite.py     # прогон Gold Dataset
python finops.py         # замер расхода токенов и расчёт TCO
```

`finops.py` на П8 запускается дважды: первый прогон снимает замер «до»
и сохраняет его на диск, второй — после вашей оптимизации — снимает «после»
и печатает сравнение. Начать замеры заново: `python finops.py --reset`.

### Проверка бэкенда без интерфейса

Веб-интерфейсу нужен браузер, боту — токен VK, `test_suite.py` работает
с практики 6, а `finops.py` — с восьмой. Чтобы получить ответ системы
без всего этого, обратитесь к ядру напрямую:

```python
import logging
logging.basicConfig(level=logging.INFO)

from orchestrator import Orchestrator

o = Orchestrator()
print(o.handle("check", "ваш вопрос"))
o.close()
```

Это тот же путь, которым идут оба канала: guardrails, память, интент, роль,
поиск через MCP, сборка промпта, модель. В журнале при этом видна строка
с активной ролью, числом найденных фрагментов и длиной промпта — по ней
удобно понимать, что происходит внутри. Способ пригодится на практике 4
при проверке переноса контекста, на пятой — при рубежном контроле,
и на седьмой — при отладке фильтров безопасности.

### Когда модель недоступна: `LLM_BACKEND=fake`

Кроме `gigachat` и `ollama` есть третий бэкенд — офлайн-заглушка `fake_llm.py`.
Она не ходит в сеть, не требует ключей и не пользуется общими знаниями: ответ
собирается из фрагментов, которые нашёл поиск. Включается одной строкой в `.env`:

```
LLM_BACKEND=fake
```

Когда она уместна: кончилась квота или пропала сеть посреди занятия; нужно
проверить автомат ролей (П3), интерфейс (П6) или guardrails (П7), не тратя
запросы к модели; рубежный контроль П5 поднимается с чистого клона до того,
как вы завели ключи.

Чего заглушка не делает:

- **не имитирует качество ответа.** Судья на П6 оценит выписку из фрагмента,
  а не работу модели — Faithfulness на ней мерить бессмысленно;
- **не годится для П8.** Расход токенов на ней ненастоящий, считать TCO не по чему;
- **не заменяет практику 4.** `GigaChatClient` и `OllamaClient` вы пишете сами,
  они входят в критерии приёмки.

**Работа, сданная на `LLM_BACKEND=fake`, не принимается.** Заглушка — инструмент
отладки, а не бэкенд для сдачи: на ней система отвечает связно и со ссылками
на источники, поэтому со стороны выглядит рабочей, хотя модель не вызывается
ни разу. Чтобы это не прошло незамеченным, `app.py` показывает плашку,
а в лог при запуске уходит предупреждение.

## Часть 3. Устройство проекта

Ядро ничего не знает о канале доставки. И веб-интерфейс, и VK-бот вызывают одну
функцию `orchestrator.handle(session_id, text)` — поэтому поиск, память, промпты
и защита от инъекций работают в обоих каналах одинаково, и добавить третий канал
можно, не трогая ядро.

```
app.py (Streamlit)   vk_bot.py (VK)
        └───────┬───────┘
                ▼
        orchestrator.handle()
                │
   ┌────────────┼─────────────┬──────────────┐
   ▼            ▼             ▼              ▼
guardrails   mcp_client   memory        prompts
   (П7)      → mcp_server   (П5)          (П4)
                 (RAG)                      │
                   │                        ▼
                   ▼                   llm_client
               ChromaDB                (П4) → GigaChat | Ollama | fake
                 (П2)
```

| Файл | Практика | Кто пишет |
| --- | --- | --- |
| `README.md` | П1 | студент |
| `ingest.py` | П2 | студент (очистка, чанкинг, рубрикация; замер `evaluate_retrieval()` готов) |
| `gold_dataset.json` | П2 → П6 | студент: 5 вопросов на П2, расширение до 10 на П6 |
| `orchestrator.py` | П3 | студент (роли, интенты, граф переходов) |
| `llm_client.py` | П4 | студент |
| `prompts.py` | П4 | студент |
| `memory.py` | П5 | студент |
| `app.py` | П6 | студент (оформление) |
| `test_suite.py` | П6 | студент |
| `guardrails.py` | П7 | студент |
| `finops.py` | П8 | студент (расчёт TCO, эффект оптимизации) |
| `reports/` | П2, П6, П8 | студент: протокол замеров, отчёт по метрикам, расчёт TCO |
| `config.py`, `contracts.py`, `mcp_server.py`, `mcp_client.py`, `vk_bot.py`, `fake_llm.py` | — | готово, менять не нужно |

### Что нельзя менять

`contracts.py` и сигнатуры `orchestrator.handle()`, `memory.save()`, `memory.window()`,
`LLMClient.generate()`. На них завязаны оба канала и тесты: измените контракт —
и работать перестанет всё сразу.

### Два вида заглушек

Незаполненные места ведут себя по-разному, и это намеренно:

- **`raise NotImplementedError`** — в `ingest.py`, `llm_client.py`, `prompts.py`,
  `orchestrator.detect_intent()`, `finops.estimate_tco()`. Без них система не работает
  в принципе, поэтому они падают громко, а не возвращают `None` втихую.
- **Безопасная заглушка** — в `memory.py` (не сохраняет, возвращает пустую историю)
  и `guardrails.py` (пропускает всё). Ядро обращается к ним начиная с практики 3,
  а пишете вы их на практиках 5 и 7. До этого система работает — просто забывчивая
  и незащищённая.

### Порядок сборки

Практики 2–4 дают первый сквозной ответ. На практике 3 сквозного ответа ещё нет:
проверяйте автомат отдельно, вызовом `detect_intent()` и `route()` на наборе фраз.
Практика 5 — рубежный контроль: практики 2–5 должны работать вместе с чистого клона
строго по этой инструкции.

Две метрики, которые легко перепутать. **hit-rate@5** — попал ли фрагмент с ответом
в первые пять результатов; считается механически сверкой `source`, доступен с П2.
**Context Precision** из триады RAG — насколько найденное относится к вопросу;
оценивает LLM-судья, появляется на П6. В отчёте это два разных числа.

Практика 8 считает деньги и потому идёт последней: `finops.py` опирается на
`orchestrator.usage`, который наполняется только когда работает весь конвейер.
Замеры «до» и «после» делаются на одном и том же эталонном диалоге — иначе они
несравнимы, — и двумя отдельными запусками: оптимизация меняет `config.py`,
поэтому в одном процессе оба замера не снять.

Отчёты по практикам 2, 6 и 8 пишутся в `reports/` — там лежат заготовки
с разделами. В отличие от базы поиска и исходных данных, отчёты **входят
в репозиторий**: приёмка асинхронная и идёт по тому, что попало в бандл.
